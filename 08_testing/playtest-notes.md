# Playtest Notes

## Purpose

Capture real testing observations in a structured way so Neo UO can learn from actual play instead of vague memory.

This file is not only for bugs.
It is for tracking whether the intended experience is landing.

## Core Rule

Every meaningful playtest entry should preserve the difference between:

- what was tested
- what happened
- what it felt like
- and what should happen next

## Entry Standard

Each playtest entry should eventually include:

- date
- build or rule state
- testers
- test focus
- setup notes
- observations
- what felt strong
- what felt bad
- interpretation
- recommended next action

## Interpretation Rule

Whenever possible, classify findings as one of the following:

- design success
- design failure
- tuning issue
- clarity issue
- operational/setup issue
- unknown / needs repeat test

This helps the project avoid treating every bad test as a full design collapse.

## What Strong Playtest Notes Look Like

Strong notes are:

- specific
- tied to a scenario
- tied to a build or ruleset state
- clear about what was actually experienced
- clear about what should be tested next

Weak notes are:

- broad
- emotional only
- disconnected from a scenario
- impossible to reproduce

## Early Priority Areas for Playtests

The most important early findings will likely come from:

- death and continuity feel
- wound and recovery feel
- tracking readability
- combat pacing direction
- ecology pressure and movement feel
- tension vs frustration balance

## Example Entry Skeleton

### Date

YYYY-MM-DD

### Build / Ruleset State

Short identifier or note.

### Testers

Names or shorthand.

### Focus

What was actually being tested.

### Setup

Any artificial setup or special assumptions.

### What Happened

Short factual summary.

### What Felt Strong

What worked.

### What Felt Bad

What did not work.

### Interpretation

What category the finding belongs to.

### Next Action

What should be changed, tested again, or clarified.

## Current Direction

Neo UO playtest notes should become a reliable memory system for the project, with emphasis on experience truth rather than only bug logging.
